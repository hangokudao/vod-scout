# VOD Scout v0.5.0 품질·작업 대기열 개선 계획

상태: **G1~G7 구현·자동 검증 PASS · GTX 1060 직접 GPU·CPU 음성 인식 PASS · 30초 구성요소 자원 측정 MEASURED_NO_THRESHOLD 완료 · 실제 YouTube/reference 전체 흐름·자동 GPU→CPU 제품 전환·Windows UI·1~8시간/동일 입력 자원 비교·G7 병렬 HOLD 또는 BLOCKED**

릴리스 게이트와 결과 기록: [v0.5.0 릴리스 작업 정본](V0.5.0-RELEASE.md)

현재 공개 정본은 v0.4.0이고, 이 worktree의 소스·로컬 패키지 후보 버전은 **v0.5.0**이다. 공개 v0.5.0 Release·다운로드 URL은 아직 만들지 않는다.

## 누구를 위한 기능인가

- 플랫폼: Twitch가 아니라 **치지직 스트리머 중심**
- 방송 형태: 버츄얼 스트리머의 저스트채팅과 게임
- 화면 특징: 방송 화면 안에 채팅창 오버레이가 있음
- 핵심 목표: 여러 개의 긴 영상을 맡겨 두면 순서대로 분석하고, 실제로 검토할 만한 편집 후보를 충분히 많이 보여 주는 것
- 기본 원칙: Twitch 마커나 Twitch API가 없어도 핵심 기능이 동작해야 함

## 확정된 입력 환경과 판단 원칙

- 주요 방송 규모는 시청자 약 5~30명이다.
- 채팅은 방송 화면 안의 익명 오버레이이므로 작성자 ID와 서로 다른 참여자 수를 알 수 있다고 가정하지 않는다.
- 채팅은 절대 개수나 참여자 수가 아니라, 현재 VOD 안에서 확인 가능한 고정 채팅 영역의 평소 움직임 분포보다 활동이 늘었는지를 본다. 실제 메시지 수나 새 메시지 수로 표현하지 않는다.
- 채팅 활동만으로 후보를 만들지 않고 오디오 반응, 말하기 변화 또는 화면 사건과 함께 보조 신호로 사용한다.
- 현재 움직임 분석만으로 일반 문장과 이모티콘을 구분할 수 없으므로 구분했다고 표시하거나 점수에서 임의로 제외하지 않는다.
- 채팅 신호가 없거나 신뢰하기 어려우면 감점하지 않고, 확인 가능한 다른 신호만으로 점수를 계산한다.

## 작업 순서

| 순서 | 작업 | 결과 |
|---:|---|---|
| 1 | YouTube 자막 확보·검증 | 한국어 자동 자막을 우선하고, 없거나 사용할 수 없을 때만 제작자 한국어 자막을 사용하며, 두 자막이 없거나 검증할 수 없는 구간은 로컬 Whisper로 대체 |
| 2 | GPU·CPU Whisper 실행과 사용자 제어 | 실제 GPU 시험 성공 뒤에만 사용하고 `자동`·GPU·CPU·속도·정확도·CPU 사용량을 제어 |
| 3 | 기존 음성 인식 품질 안전장치와 선택 후보 재음성 인식 | 반복·깨진 문자를 안전하게 표시하고 사용자가 고른 후보만 다시 음성 인식 |
| 4 | 분석 중 렉 조사와 자원 제한 | 어느 단계에서 느려지는지 측정하고 앱 조작이 멈추지 않도록 제한 |
| 5 | 후보 수와 내용 품질 | 8·20·30개 설정과 후보 근거·품질 경고를 일관되게 적용 |
| 6 | 여러 영상 작업 대기열 | 여러 영상을 등록하고 기본적으로 한 개씩 순서대로 처리 |
| 7 | 제한적 병렬 처리 | 순차 대기열이 안정된 뒤 자원이 충분한 PC에서만 선택 제공 |

1~7은 모두 v0.5.0 범위다. 현재 G1~G7 구현과 자동 테스트, GTX 1060 직접 GPU·CPU 음성 인식은 PASS이며, 30초 구성요소 자원 측정은 `MEASURED_NO_THRESHOLD`로 완료했다. 실제 YouTube/reference 전체 흐름·자동 GPU→CPU 제품 전환·Windows UI·1~8시간/동일 입력 자원 비교는 HOLD 또는 BLOCKED다. G7 병렬 옵션은 측정 전까지 disabled/HOLD다.

## 이번 버전의 비범위

아래 항목은 v0.4.0 이후 아이디어로 남기되 v0.5.0 구현에 섞지 않는다.

- YouTube 자막 검색 UI와 검색 결과의 원본 시각 이동
- 수분 단위 이야기 후보와 멀리 떨어진 관련 장면 연결
- 채팅 글자 인식, 작성자 식별, 채팅 영역 자동 탐색
- 사용자 API와 외부 AI를 이용한 후보 재정렬
- 완성 쇼츠 렌더링과 자동 게시
- Windows Authenticode 인증서 구매·적용

이 항목들은 별도 승인과 별도 버전 없이 구현하지 않는다.

## 1. YouTube 자막 확보·검증

YouTube 입력은 다음 순서로 자막을 확인한다. 일반 VOD에서는 한국어 자동 자막을 먼저 사용하고, 자동 자막이 없거나 사용할 수 없을 때만 제작자 한국어 자막을 사용한다. 두 자막이 없거나 검증할 수 없는 구간만 로컬 Whisper로 확인한다. 자동 번역 자막, 다른 언어 트랙, `live_chat`은 선택·색인하지 않는다.

### 필요한 동작

1. 자막과 모든 분석 구간의 시간 기준은 원본 영상 시간으로 유지한다. 자막 표시용 상대 시각이나 다운로드 구간 시각으로 바꾸지 않는다.
2. 트랙 선택과 각 구간에 대해 시작 시각이 끝 시각보다 앞서고 두 시각 모두 원본 영상 길이 범위 안에 있는지, 겹침·중복·비정상적으로 긴 공백·일정한 시간 오프셋이 있는지를 검증하고 결과를 기록한다.
3. 실제 기준 영상으로 확인하기 전에는 시간 허용 오차나 합격 임계값을 임의로 정하지 않는다. 기준 영상과 사람이 확인한 구간을 확보한 뒤에만 필요한 판정 기준을 고정한다.
4. 자막이나 구간을 사용할 수 없거나 품질이 낮거나 검증할 수 없으면 해당 자막·구간을 신뢰하지 않고 필요한 범위를 로컬 Whisper로 처리한다. 자막 확인 실패가 작업 전체 실패가 되지 않게 한다.
5. 작업 데이터에 원본 자막 파일, 제작자 제공인지 자동 생성인지, 언어, 트랙 식별자, 파일 SHA-256을 저장한다. 재개할 때는 같은 자막 개정과 해시를 사용한다.
6. 자막 검색 UI와 검색 결과에서 원본 시각으로 이동하는 기능은 이 버전의 비범위다. 이 버전은 분석 근거와 로컬 대체 처리만 계약한다.

### 현재 상태와 완료 조건

- 구현·자동 검증: **PASS**.
- 실제 자막 기준 영상 검증과 실제 시간 오프셋 판정: **HOLD**.
- 한국어 자동 자막 우선, 자동 자막이 없거나 사용할 수 없을 때 제작자 한국어 자막 대체, 제외 트랙, 원본 시간 기준, 검증 항목, 두 자막이 없거나 검증할 수 없는 구간의 Whisper 대체와 작업 데이터 메타데이터를 테스트에서 확인한다.

## 2. GPU·CPU Whisper 실행과 사용자 제어

### 필요한 동작

1. 사용자가 `자동(GPU 우선)`, `GPU`, `CPU` 중 실행 모드를 고를 수 있게 한다. `빠르게`, `균형`, `정확하게` 속도·정확도 단계를 제공하고 CPU 사용량·스레드 수를 자동 또는 사용자가 제어할 수 있게 한다.
2. GPU 이름이나 드라이버가 있다는 사실만으로 지원한다고 판단하지 않는다. 짧은 시험 음성 인식에서 GPU 백엔드가 실제로 로드되고 결과가 생성된 경우에만 GPU를 사용한다.
3. 자동 모드는 시험 성공 뒤 GPU를 우선한다. GPU 모드를 선택했어도 시험 또는 실행이 실패하면 이유를 기록하고 CPU로 대체한다. GPU가 없는 PC에서도 CPU 경로로 작업을 완료한다.
4. GPU 메모리 부족, 드라이버 오류, 실행 파일 오류가 발생하면 실패한 청크만 CPU로 처리한다. CPU와 GPU가 같은 청크를 동시에 처리하지 않는다.
5. 같은 청크의 GPU→CPU 전환은 한 번만 허용한다. CPU도 실패하면 `FAILED`를 유지하고 자동 재시도하지 않는다.
6. 장치, 모델, 속도·정확도 단계, CPU 제어값, 처리 시간과 GPU 실패·CPU 대체 처리의 시작·완료·실패 상태를 작업 데이터에 저장한다. GPU 실패가 기록된 청크는 앱 재실행 뒤 GPU를 다시 호출하지 않는다.

### 현재 상태와 완료 조건

- 구현·자동 검증: **PASS**.
- GTX 1060 직접 GPU·CPU 시험·실행: **PASS**. 제품 자동 GPU→CPU 대체 처리와 사용자 설정·화면 흐름 검증: **HOLD**.
- CPU와 GPU가 동일한 체크포인트·원본 타임코드 형식을 사용하고, GPU 실패 뒤 작업 전체를 다시 시작하지 않는지 확인한다.

## 3. 기존 음성 인식 품질 안전장치와 선택 후보 재음성 인식

기존 이상 음성 인식 안전 구현은 G3에서 품질 안전장치로 보존·검증한다. 구현·자동 테스트는 PASS이며, 실제 표본과 사용자 흐름은 별도 HOLD다.

### 필요한 동작

1. 한 글자·음절·짧은 단어·짧은 문장의 비정상 반복과 깨진 문자를 별도 품질 상태로 기록하고 `음성 인식 결과 불확실`을 표시한다. 원본 결과와 진단 이유는 보존한다.
2. 불확실한 문장은 후보 제목 재료에서 제외하지만 오디오·화면 근거가 있는 후보 자체를 자동 삭제하지 않는다. 웃음·감탄·노래·의도적인 반복 발언은 일괄 제거하지 않는다.
3. 사용자가 선택한 후보만 승인된 설정·모델 범위에서 다시 음성 인식할 수 있게 한다. 새 모델을 자동으로 내려받지 않는다.
4. 수동 재음성 인식 한 번마다 실행 ID 하나를 만들고 시작·완료·실패, 결과 개정, 원본 결과와 실패 이유를 작업 데이터에 저장한다. 완료·실패가 또 다른 재분석을 자동 호출하지 않는다.

### 현재 상태와 완료 조건

- 구현·자동 검증: **PASS**.
- 실제 반복 발언 표본, 선택 후보 재음성 인식과 사용자 흐름: **HOLD**.
- 깨진 문자가 사용자 화면·CSV·후보 제목에 노출되지 않고, 품질이 낮은 결과만으로 전체 작업이 실패하지 않는지 확인한다.

## 4. 분석 중 렉 조사와 자원 제한

`렉`을 하나의 문제로 묶지 않고 FFmpeg 오디오 생성, Whisper CPU·메모리, 채팅 영역 디코딩, 후보 미리보기 FFmpeg 중복, 목록 렌더링·재생, 취소·화면 이동 반응을 따로 측정한다.

### 필요한 동작

1. 단계별 처리 시간, CPU, 메모리, 디스크 사용량과 실행 중인 자식 프로세스 수를 기록한다.
2. 분석과 후보 미리보기 생성이 동시에 무거운 FFmpeg 작업을 중복 실행하지 않도록 조정한다.
3. 메모리·임시 파일·실행 중인 외부 도구 수에 상한을 둔다. 경고 기준과 강제 중단 기준은 측정 뒤 구분한다.
4. 분석 중에도 취소, 화면 이동, 현재 상태 확인이 가능해야 한다. 강제 기준을 넘으면 현재 작업의 자식만 종료하고 마지막 완료 체크포인트와 이유를 저장한 뒤 `FAILED`로 끝낸다.
5. 더 낮은 설정으로 자동 재시작하지 않으며 체크포인트·취소·재개·작업 데이터 보존을 약화하지 않는다.

### 현재 상태와 완료 조건

- 구현·자동 검증: **PASS**.
- 30초 구성요소 자원 측정은 `MEASURED_NO_THRESHOLD`로 완료했다. 실제 기준 영상 전체 흐름의 렉 재현, 동일 입력 변경 전후 비교, 장시간 자원 측정과 취소 후 자식 프로세스 정리: **HOLD**.

## 5. 후보 수와 내용 품질

### 후보 수

- 후보 수는 `8개`, `20개`, `30개` 중 작업별로 선택하며 기본값은 `20개`다. 후보가 부족하면 의미 없는 후보로 채우지 않는다.
- 같은 사건을 조금씩 다르게 자른 후보의 중복 제거를 유지하고 원본 시간 범위와 부당한 겹침을 검증한다.
- 후보 수 변경과 수동 재음성 인식은 기존 결과를 덮지 않는 새 개정으로 저장한다. 안정적인 동일 후보 ID의 판정만 이어받고, 새 ID는 미판정으로 시작한다. v0.4.0 정상본과 이전 개정을 보존한다.
- 30개를 한 화면에 모두 그려 렉이 생기면 목록 일부만 화면에 그린다.

### 내용 품질

후보 점수와 내용 품질을 분리한다. 깨진 문자·비정상 반복은 경고하고 제목 재료에서 제외하되 후보 자체는 자동 제외하지 않는다. 앞뒤 문장이 연결되지 않으면 경고만 표시하고, 제목 재료·화면 사건·오디오·말하기·채팅 영역 움직임 근거가 모두 없을 때만 무효 후보로 제외한다. 같은 사건·시간 범위의 중복은 낮은 순위를 제외하며, 문장만 같고 시간이 다른 후보는 자동 병합하지 않는다.

게임 승리·실패, 장면 급변, 노래·웃음·비명, 조용하지만 이어지는 대화처럼 글보다 소리·화면·맥락이 중요한 예외는 이유를 기록하고 후보를 유지할 수 있다.

### 익명 채팅 활동

- 작성자 수, 고유 참여자 수, 채팅 내용·이모티콘 종류를 점수 근거로 사용하지 않는다.
- 현재 VOD의 고정 채팅 영역 움직임 분포보다 상대적으로 늘어난 경우만 보조 신호로 기록한다. 실제 메시지 수·새 메시지·참여자 증가라고 표현하지 않는다.
- 채팅 움직임만으로 후보를 만들지 않는다. 유효 표본이 부족하거나 영역을 신뢰할 수 없으면 `확인 가능한 채팅 영역 움직임 없음`으로 처리하고 가산·감점 없이 나머지 신호로 점수를 맞춘다.

### 현재 상태와 완료 조건

- 구현·자동 검증: **PASS**.
- 실제 품질 비교, 사람 채택률·검토 시간 측정: **HOLD**.
- 후보마다 `왜 선택됨`, `무엇이 불확실함`을 확인할 수 있고, 품질 개선 주장은 같은 입력의 객관 지표와 사람 판정이 함께 개선된 경우에만 한다.

## 6. 여러 영상 작업 대기열

### 기본 동작

1. 여러 영상을 등록하고 각 영상에 독립된 작업 ID, 설정, 진행률, 체크포인트, 후보 결과를 둔다.
2. 기본 실행은 `분석 작업 1개`이며 종료 상태를 저장한 뒤 다음 작업을 시작한다. 한 영상의 실패가 다음 영상의 시작을 막지 않는다.
3. 앱 재실행 시 실행 중 작업은 `INTERRUPTED`로 복원하고 사용자 재개·취소 전에는 자동 재개하거나 다음 작업을 시작하지 않는다. 실패·취소 작업도 자동 재시작하지 않는다.
4. 대기 작업 순서 변경·개별 취소·실패 작업 재시작을 제공하고, 한 앱 인스턴스만 실행권을 갖는다.
5. 대기 순서와 실행 모드는 원자적으로 저장하고 직전 정상본을 남긴다. 작업 데이터는 영상별 폴더에 격리한다.
6. 실행 중 삭제는 `취소 요청 → 자식 프로세스 0개 확인 → 종료 상태 저장 → 정규화한 jobs/{job-id} 하위 삭제 → 대기열 참조 제거` 순서로만 수행한다. 폴더 삭제가 실패하면 참조와 `삭제 실패`를 유지한다.

### 현재 상태와 완료 조건

- 구현·자동 검증: **PASS**.
- 3개 영상 실제 흐름, 재실행 복원, 단일 실행권, 실행 중 삭제: **HOLD**.

## 7. 제한적 병렬 처리

병렬 처리는 속도 기능이 아니라 자원 관리 기능이다. 앞선 1~6 단계가 PASS가 되기 전에는 구현·측정하지 않는다.

- 기본값은 `순차 처리`다. 두 개의 Whisper 또는 두 개의 GPU 분석을 동시에 실행하지 않는다.
- 먼저 `한 영상 분석 + 다른 영상 다운로드`처럼 경쟁이 적은 조합만 시험한다.
- CPU·GPU 메모리·RAM·디스크 조건이 부족하면 순차 처리로 한 번 전환하고 상태와 이유를 저장한다. 앱 재실행 뒤 자동으로 병렬화를 다시 켜지 않는다.
- 병렬 실행 중 하나가 실패해도 다른 작업의 체크포인트와 결과를 손상시키지 않는다. 동시 실행 상한은 실제 측정 뒤 정한다.

### 현재 상태와 완료 조건

- 구현·자동 검증: **PASS**.
- 제한적 병렬 처리의 실제 안전성·총시간·피크 자원 측정: **HOLD**. 측정 전 선택 항목은 제공하지 않는다.
- 이득보다 렉·메모리·실패 증가가 크면 기능을 노출하지 않는 것으로 평가를 끝내며, 반복 튜닝을 릴리스 완료로 오인하지 않는다.

## 보류 연구: 멀리 떨어진 관련 구간 묶기

예를 들어 `10~11분`의 대화가 `1시간 10분~1시간 11분`의 결과나 후속 이야기와 연결될 수 있다. 이것은 단순한 인접 구간 연결이 아니라 **멀리 떨어진 관련 장면 찾기**에 가깝다.

가능한 결과는 두 장면을 자동으로 이어 붙이는 것이 아니라 다음처럼 보여 주는 것이다.

```text
관련 장면 묶음
- 00:10:12~00:11:03: 처음 질문하거나 약속한 장면
- 01:10:18~01:11:22: 나중에 결과가 나온 장면
```

후보 신호로는 반복된 핵심 단어, 같은 게임 목표·인물·주제, 질문과 나중의 답, 도전 선언과 결과를 생각할 수 있다. 하지만 우연히 같은 단어가 나온 장면을 잘못 연결할 위험이 크다.

따라서 이 항목은 **HOLD**다. 위 1~7의 정확성·대기열·자원 관리가 안정된 뒤 사람이 표시한 연결 사례를 모아 별도 버전에서 검토한다.
