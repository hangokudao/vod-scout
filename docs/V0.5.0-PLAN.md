# VOD Scout v0.5.0 품질·작업 대기열 개선 계획

상태: **사용자 요구사항 기록 완료 · 구현 시작 전 HOLD**

현재 공개 정본은 v0.4.0이다. 따라서 이 작업 묶음의 다음 기능 버전 이름은 **v0.5.0**으로 잡는다. 이 문서를 추가하는 작업에서는 `package.json`, `src-tauri/Cargo.toml`, `src-tauri/tauri.conf.json`의 실제 버전을 변경하지 않는다.

## 누구를 위한 기능인가

- 플랫폼: Twitch가 아니라 **치지직 스트리머 중심**
- 방송 형태: 버츄얼 스트리머의 저스트채팅과 게임
- 화면 특징: 방송 화면 안에 채팅창 오버레이가 있음
- 핵심 목표: 여러 개의 긴 영상을 맡겨 두면 순서대로 분석하고, 실제로 검토할 만한 편집 후보를 충분히 많이 보여 주는 것
- 기본 원칙: Twitch 마커나 Twitch API가 없어도 핵심 기능이 동작해야 함

## 작업 순서

| 순서 | 작업 | 결과 |
|---:|---|---|
| 1 | 이상한 음성 인식 결과 수정 | `너너너...`, 깨진 문자, 반복 문장이 제목과 후보 판단을 오염하지 않음 |
| 2 | 분석 중 렉 조사와 자원 제한 | 어느 단계에서 느려지는지 측정하고 앱 조작이 멈추지 않도록 제한 |
| 3 | 후보 8개 제한 제거 | 기본 20개를 보여 주고 사용자가 8·20·30개 중 선택 가능 |
| 4 | 후보 내용 품질 검사 | 점수가 높아도 내용이 성립하지 않는 후보는 낮추거나 별도 표시 |
| 5 | 여러 영상 작업 대기열 | 여러 영상을 등록하고 기본적으로 한 개씩 순서대로 처리 |
| 6 | GPU 우선·CPU 자동 전환 | 실제 GPU 실행이 확인될 때만 사용하고 실패한 청크는 CPU로 완료 |
| 7 | 제한적 병렬 처리 | 순차 대기열이 안정된 뒤 자원이 충분한 PC에서만 선택 제공 |

1~6은 v0.5.0의 핵심 작업 후보다. 7은 작업 목록에는 포함하지만 안정성 검사를 통과하지 못하면 기본값으로 켜지 않는다.

## 1. 이상한 음성 인식 결과 수정

### 현재 보이는 문제

- `너너너너...`처럼 한 글자나 짧은 문구가 비정상적으로 반복된다.
- 잘못된 UTF-8 바이트가 `�`로 바뀐 채 사용자 화면에 노출될 수 있다.
- 품질이 나쁜 음성 인식 결과가 후보 제목과 요약으로 그대로 사용된다.
- 오디오·채팅 점수가 높으면 내용이 이상해도 상위 후보가 될 수 있다.

### 필요한 동작

1. 한 글자, 음절, 짧은 단어, 짧은 문장이 비정상적으로 반복되는 비율을 계산한다.
2. 반복이 의심된다고 실제 방송 내용을 바로 삭제하지 않는다. 원본 결과를 진단용으로 남기고 `음성 인식 결과 불확실` 상태를 붙인다.
3. 잘못된 바이트가 발견되면 `�`를 숨기는 것으로 끝내지 말고, 파일 인코딩과 Whisper 출력 단계 중 어디서 깨졌는지 기록한다.
4. 불확실한 문장은 후보 제목의 재료로 사용하지 않는다.
5. 웃음, 감탄, 노래, 의도적으로 같은 말을 반복한 장면까지 일괄 제거하지 않도록 실제 버츄얼 방송 표본으로 검사한다.
6. 사용자가 선택한 후보만 더 정확한 설정이나 모델로 다시 음성 인식할 수 있게 한다.

### 완료 조건

- `너너너...`와 `�`가 포함된 회귀 자료가 자동 테스트에 있다.
- 깨진 문자가 사용자 화면, CSV, 후보 제목에 그대로 나오지 않는다.
- 반복 오류를 제거한 뒤에도 실제 반복 발언과 웃음·감탄을 보존하는 사례를 기록한다.
- 품질이 낮은 음성 인식 결과만 있어도 작업 전체가 실패하지 않는다.

## 2. 분석 중 렉 조사와 자원 제한

### 먼저 구분할 것

`렉`을 하나의 문제로 묶지 않고 아래를 따로 측정한다.

- FFmpeg가 오디오를 만드는 동안의 CPU·디스크 사용
- Whisper 음성 인식 중 CPU·메모리 사용
- 채팅 영역 움직임 분석 중 영상 디코딩 사용
- 후보 미리보기 생성 중 FFmpeg 중복 실행
- React 화면의 목록 렌더링과 영상 재생 끊김
- 취소 버튼, 작업 화면 이동 등 앱 조작 반응

### 필요한 동작

1. 단계별 처리 시간, CPU, 메모리, 디스크 사용량과 실행 중인 자식 프로세스 수를 기록한다.
2. 분석과 후보 미리보기 생성이 동시에 무거운 FFmpeg 작업을 중복 실행하지 않도록 조정한다.
3. Whisper 스레드 수가 PC의 모든 CPU 자원을 계속 차지하지 않도록 자동값과 사용자 설정을 둔다.
4. 메모리·임시 파일·실행 중인 외부 도구 수에 상한을 둔다.
5. 분석 중에도 취소, 화면 이동, 현재 상태 확인이 가능해야 한다.
6. 원인을 측정하기 전에 임의로 스레드 수나 메모리 합격선을 확정하지 않는다.

### 완료 조건

- 같은 실제 영상으로 변경 전후 처리 시간과 앱 반응을 비교한 기록이 있다.
- 분석 중 앱 화면이 멈추는 경우를 재현하고 원인 단계를 구분한다.
- 취소 후 FFmpeg·Whisper·GPU 관련 자식 프로세스가 남지 않는다.
- 성능을 줄이기 위해 체크포인트, 취소·재개, 작업 데이터 보존을 약화하지 않는다.

## 3. 후보 8개 제한 제거

### 필요한 동작

- 백엔드에 고정된 상위 8개 제한을 설정값으로 바꾼다.
- 초기 UI 선택값은 `8개`, `20개`, `30개`로 제공하고 기본값은 `20개`로 시작한다.
- 후보 수를 늘려도 같은 사건을 조금씩 다르게 자른 후보가 목록을 채우지 않도록 중복 제거를 유지한다.
- 후보 ID와 사용자의 채택·보류·제외 상태는 정렬과 재분석 뒤에도 유지한다.
- 30개를 한 화면에 모두 그려 렉이 생기면 목록 일부만 화면에 그리는 방식을 사용한다.

### 완료 조건

- 같은 입력에서 8·20·30개 설정이 각각 적용된다.
- 20개 이상 결과의 원본 시간이 분석 범위 안에 있고 서로 부당하게 겹치지 않는다.
- 앱을 다시 열어도 선택값과 후보 판정이 복원된다.
- 후보 수가 부족한 영상은 의미 없는 후보로 개수를 억지로 채우지 않는다.

## 4. 후보 내용 품질 검사

후보 점수와 내용 품질을 분리한다. 큰 소리나 채팅 움직임이 있었다는 이유만으로 좋은 편집 후보라고 단정하지 않는다.

### 후보를 낮추거나 경고할 조건

- 깨진 문자 또는 비정상 반복 비율이 높음
- 음성 인식 결과와 앞뒤 문장이 연결되지 않음
- 제목으로 쓸 만한 내용이 없고 화면 사건 근거도 없음
- 같은 문장이 여러 후보에 반복됨
- 오디오 한 번의 피크만 있고 전후 반응이 없음

### 후보를 유지할 수 있는 예외

- 말이 없어도 게임 승리·실패, 장면 급변, 채팅 급증이 함께 확인됨
- 노래, 웃음, 비명처럼 글로 옮긴 내용보다 소리 자체가 중요한 장면
- 저스트채팅에서 조용하지만 앞뒤 대화가 하나의 사건으로 이어짐

### 완료 조건

- 후보마다 `왜 선택됨`, `무엇이 불확실함`을 짧게 확인할 수 있다.
- 음성 인식 품질이 나쁘다는 이유만으로 게임 화면의 명확한 사건까지 모두 버리지 않는다.
- 점수 순위와 사람이 채택한 비율을 함께 기록해 품질 변경 전후를 비교한다.

## 5. 여러 영상 작업 대기열

### 기본 동작

1. 지원하는 영상 여러 개를 한 번에 등록한다.
2. 각 영상은 독립된 작업 ID, 설정, 진행률, 체크포인트, 후보 결과를 가진다.
3. 기본값은 `분석 작업 1개`이며 첫 작업이 끝나면 다음 작업을 자동으로 시작한다.
4. 앱을 닫았다 열어도 대기 순서와 완료·실패·취소 상태를 복원한다.
5. 사용자는 대기 작업의 순서 변경, 개별 취소, 실패 작업 재시작을 할 수 있다.
6. 한 영상의 실패가 다음 영상의 시작을 막지 않는다.

### 완료 조건

- 최소 3개 영상을 등록해 `대기 → 분석 중 → 검토 준비`가 순서대로 진행된다.
- 두 번째 영상을 기다리는 동안 첫 번째 영상 결과를 검토할 수 있다.
- 앱 강제 종료 후 마지막 완료 지점과 대기 순서가 복원된다.
- 서로 다른 영상의 임시 파일, 체크포인트, 후보가 섞이지 않는다.

## 6. GPU 우선 사용과 CPU 자동 전환

### 필요한 동작

1. 설치된 GPU 이름만 보고 지원한다고 판단하지 않고 짧은 시험 음성 인식을 실행한다.
2. GPU 백엔드가 실제로 로드되고 결과가 생성된 경우에만 GPU 경로를 사용한다.
3. GPU 메모리 부족, 드라이버 오류, 실행 파일 오류가 발생하면 실패한 청크만 CPU로 다시 처리한다.
4. CPU와 GPU가 같은 청크를 동시에 중복 처리하지 않는다.
5. 후보 결과에는 사용한 장치, 모델, 처리 시간과 자동 전환 여부를 기록한다.
6. GPU가 전혀 없는 PC에서도 전체 작업이 완료돼야 한다.

### 완료 조건

- 지원 GPU, 지원하지 않는 GPU, GPU 메모리 부족, CPU 전용 PC를 각각 검사한다.
- GPU 실패 뒤 작업이 처음부터 다시 시작되지 않는다.
- CPU와 GPU 결과가 같은 체크포인트와 후보 타임코드 형식을 사용한다.
- 실제 시험하지 않은 GPU를 지원 목록이나 홍보 문구에 넣지 않는다.

## 7. 제한적 병렬 처리

병렬 처리는 속도 기능이 아니라 자원 관리 기능으로 다룬다. 순차 대기열이 안정되기 전에는 시작하지 않는다.

### 원칙

- 기본값은 꺼짐이다.
- 두 개의 Whisper 또는 두 개의 GPU 분석을 동시에 실행하지 않는다.
- 먼저 `한 영상 분석 + 다른 영상 다운로드`처럼 서로 경쟁이 적은 조합부터 시험한다.
- CPU, GPU 메모리, RAM, 디스크 여유가 기준보다 부족하면 자동으로 순차 처리로 돌아간다.
- 병렬 실행 중 하나가 실패해도 다른 작업의 체크포인트와 결과를 손상시키지 않는다.
- 동시 실행 수는 실제 하드웨어 측정 뒤 상한을 정한다.

### 완료 조건

- 같은 입력 묶음으로 순차 처리와 제한적 병렬 처리의 총시간·피크 자원을 비교한다.
- 총시간 이득보다 렉·메모리·실패 증가가 크면 기능을 켜지 않는다.
- 사용자가 병렬 처리를 끄면 항상 분석 작업 하나만 실행된다.

## 보류 연구: 멀리 떨어진 관련 구간 묶기

예를 들어 `10~11분`의 대화가 `1시간 10분~1시간 11분`의 결과나 후속 이야기와 연결될 수 있다. 이것은 단순한 인접 구간 연결이 아니라 **멀리 떨어진 관련 장면 찾기**에 가깝다.

가능한 결과는 두 장면을 자동으로 이어 붙이는 것이 아니라 다음처럼 보여 주는 것이다.

```text
관련 장면 묶음
- 00:10:12~00:11:03: 처음 질문하거나 약속한 장면
- 01:10:18~01:11:22: 나중에 결과가 나온 장면
```

후보 신호로는 반복된 핵심 단어, 같은 게임 목표·인물·주제, 질문과 나중의 답, 도전 선언과 결과를 생각할 수 있다. 하지만 우연히 같은 단어가 나온 장면을 잘못 연결할 위험이 크다.

따라서 이 항목은 **HOLD**다. 위 1~7의 정확성·대기열·자원 관리가 안정된 뒤 사람이 표시한 연결 사례를 모아 별도 버전에서 검토한다.

## 구현 시작 전 필수 확인

1. `origin/main`의 최신 v0.4.0에서 만든 별도 clean worktree와 `codex/` 작업 브랜치를 사용한다.
2. 현재 사용자 소유 변경이 있는 작업 폴더에서 구현하거나 빌드 산출물을 덮어쓰지 않는다.
3. 먼저 반복 오류와 렉을 재현하는 기준 영상을 정하고, 사용 권한과 보관 범위를 확인한다.
4. 체크포인트와 기존 v0.4.0 작업 데이터 호환 방식을 코드보다 먼저 정한다.
5. 기능별 최소 테스트와 실제 사용자 흐름을 통과한 뒤 다음 작업으로 넘어간다.
6. 실제 버전을 올릴 때만 세 버전 정본, 릴리스 문서, 변경 이력, 디버깅 기록, 인계서, 빌드 명세를 함께 갱신한다.

## v0.5.0 완료 판정

다음 조건을 모두 확인하기 전에는 v0.5.0 완료로 표시하지 않는다.

- 이상한 반복과 깨진 문자가 후보 제목·요약을 오염하지 않음
- 렉의 원인과 변경 전후 자원 사용 기록이 있음
